# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

EVA-UI is a personal UI study: recreations of Neon Genesis Evangelion style screens in HTML and CSS, with vanilla JavaScript added where a screen needs to be interactive. Each study lives in its own folder holding an `index.html` and a `style.css`, plus a `script.js` once it has behavior. A study has a code, a letter for the type of screen plus a number: `W-1` is the first Warning screen, `C-1` the first Countdown, `M-1` the MAGI screen and `T-1` the first Tactical (map) screen. The code is written uppercase in prose and as the folder name in lowercase (`w-1/`, `c-1/`), because hosted servers are case sensitive and lowercase is the URL convention. Pick a new letter to fit the screen type rather than assuming `W`, and keep a letter for one kind of screen: the map is `T`, not a second `M`, so more MAGI screens can follow `M-1`. `M-1` is the MAGI study: `data-state` on the stage and `data-status`/`data-vote` on each plate drive it, with the deliberation timers in `script.js`; after each run the motion field picks the next preset from `MOTIONS` at random unless the person typed their own; RESET fills in a fresh preset either way. Any typed motion or question (up to 44 characters) gets voted on, and the result box drops to two smaller lines once it passes 22. Presets are motions (APPROVED/DENIED, 承認/否定); anything typed is a question and is worded YES/NO (肯定/否定), including the menus. This is only text in `script.js` (`WORDS`), since the vote stays approve/deny in the attributes. It is the first with WebGL: `webgl.js` makes a canvas behind the DOM and draws a fullscreen shader from those same attributes (it only reads them), so text and state stay in HTML and the canvas is removed if WebGL is unavailable. `webgl.js` is wrapped in a function because it shares the global scope with `script.js`. Under reduced motion it draws a static frame and redraws only when an attribute changes. Its `references/` folder holds reference images and is gitignored. There is no build step, package manager, linter or test suite. Do not add any without asking. `W-1` began CSS only and later gained a `script.js` (countdown, status words, fit); `C-1` was the first study built with one.

## The homepage

The repo root holds the published homepage, `index.html` and `style.css`, with no script. It is not a study, so the self-contained rule below does not apply to it, but it uses the same palette family and registration marks. The study list is a hand-written `<ol>` of `<li>` blocks, one per study, with a copyable template in a comment above it. Add a block there when a study is added, and keep links relative (`w-1/`, no leading slash) so it works on a GitHub Pages project site.

## Running a study

Open `<study>/index.html` (for example `w-1/index.html`) directly in a browser. Fonts load from Google Fonts, so a network connection is needed for the intended look. To screenshot or measure the rendered page, serve the folder (`python3 -m http.server` from the repo root) rather than relying on reading the CSS.

## Conventions that hold across studies

- **Each study is self-contained.** Its own `index.html`, `style.css` and `script.js`, no shared stylesheet or shared script. Copying a folder to start the next study is the intended workflow.
- **The stylesheet is a teaching document.** It is ordered top to bottom as variables, layout, type, graphics, motion, with numbered section headers and comments explaining why each technique is used. Keep that order and keep the comments when editing. Add new rules to the matching section.
- **Palette lives in `:root` variables** (`--accent`, `--ink`, `--bg`, plus the three `--font-*` families). Change colors there, not on individual rules.
- **Fixed-size stage.** W-1 is a 1280x720 `.screen` with `overflow: hidden`, and everything inside is positioned relative to it. It is centered, scaled to the window with the same `fit()` and rotate prompt as C-1, and carries the same registration marks on the `body` as C-1 (in dim red). Its `script.js` counts down 30 seconds against a fixed end time (readout is minutes:seconds:hundredths, redrawn every frame, once a second under reduced motion), steps the AUTO RESPONSE and OUTER SHUTTER words from a `STEPS` table, flags a word that is still changing with `data-pending` (CSS blinks it), sets `data-state` (counting or sealed) and starts over 6 seconds after zero. Its frame detail (corner brackets, ruler ticks, inner rule) is all pseudo-elements and `box-shadow` on `.frame`, so the look stays in CSS, and `--accent-dim` is the second red used for decoration. C-1 centers its stage with `display: grid` on `body` and `margin: auto` on `.screen`, and `script.js` publishes a `--scale` custom property that `.screen` applies with `zoom` (not `transform`, so the layout size shrinks too). The fit leaves a 48px margin (12px on narrow windows) so the registration marks drawn on the `body` background stay visible around the stage. Portrait phones under 600px wide get a rotate prompt instead, since the page cannot lock orientation. The scale is measured from `documentElement.clientWidth`/`clientHeight` and the viewport meta carries `minimum-scale=1`; without both, a mobile browser widens the layout viewport to the 1280px stage and the fit and the 600px rotate query both misread the screen. The `sweep` keyframe hardcodes `720px`, so changing the screen height means changing that too.
- **CSS owns the look, JS owns the behavior.** Looping motion stays in CSS (`@keyframes` with `steps()` for hard blinks). JavaScript handles state and interaction, and drives the look by toggling classes, `data-*` attributes or CSS custom properties, never by writing inline styles. Keep it plain vanilla JS in a `script.js` loaded with `defer`, with no libraries, bundler or build step.
- **C-1 is the model for the split.** Each seven-segment digit is a `.digit` with a `data-v` attribute (0 to 9), and a single CSS table maps each value to its lit segments, so `script.js` never touches individual segments. `data-state` on `.screen` (`idle`, `running`, `done`) drives the power-source swap (INTERNAL from the moment the countdown starts, back to EXTERNAL on reset) and the whole end-of-countdown alert (red backdrop, warning label, hazard bands, red digits). Those pieces sit in the markup from the start and `done` just reveals them, so the alert animations stay in CSS. `aria-current` on a mode label drives its highlight. The end-of-countdown alarm is `C-1/sounds/alarm.mp3`, played twice with a 500ms gap by `script.js`; START unlocks audio with a muted play because browsers need a gesture first, and leaving the done state cuts it off. The countdown measures time against a fixed end timestamp each frame, not by accumulating ticks. The controls row is `hidden` in the HTML until the script runs.
- **Reduced motion applies to both.** Every CSS animation class is switched off or paused under `prefers-reduced-motion`, and a new one must be added to that media query. JS that animates or auto-updates should check `matchMedia('(prefers-reduced-motion: reduce)')` and fall back to a static state.
- **Studies degrade without JS where practical.** Start from the working CSS-only version and layer behavior on top, so the page still shows something sensible if the script fails.
- **Japanese text** carries `lang="ja"`. Letter-spaced text needs a matching `padding-left` to stay optically centered (see `.title-en`).
- **SVG parts are styled with `stroke` and `fill`**, not `border` and `background` (see `.hex`).
- **`T-1` is the map study.** `script.js` draws three nested maps into empty `<svg>` elements from `GEO.japan`, `GEO.kanto` and `GEO.hakone` (Web Mercator, written by hand, no library). `REGIONS` holds each map's center and width in degrees, and each marks the next one with a small box; the panel size is read from the svg's `viewBox`. All colors and line widths live in `style.css`, and the glow is a `drop-shadow` on a group. The moving parts (route, trail, contact, shots) are in a second `svg.live` laid over the panel so the contact shows above the log box. The Tokyo-3 city is fictional and drawn in `city()`, not from data. The map page credits OpenStreetMap contributors in its key. A scenario runs on top, with the M-1 state machine (`data-state` idle, running or resolved on `.screen`, `data-level` for the highest site status, `data-status` idle, alert or breach on each site and on the city): DETECT starts an unknown contact, from Sagami or Suruga Bay (hand-drawn routes) or any compass bearing (`routeFrom`, timed to cross the Hakone map's edge at the same second whatever the direction, since the city sits near its top; RANDOM is any bearing at all), driven by a fixed list of timed events (`buildEvents`) fired from the clock each frame, and it is either contained at the perimeter or breaches Tokyo-3. Colors are teal idle, amber alert, red breach, and everything that changes in the strip and the red-framed event log (`role="log"`) follows from those attributes. Not built: a real feed (USGS earthquakes is the candidate) and runtime region loading.
- **Map data is baked, not fetched at runtime.** `tools/geo.mjs` (Node built-ins only, run by hand, never by a page) writes `t-1/data/<region>.js` as `GEO.<region> = {bbox, ...}`: `land` mode from Natural Earth (public domain) for overview regions, `detail` mode from OpenStreetMap through Overpass for local ones (roads, rivers, rail, water, peaks; ODbL, so a page that uses it must credit "OpenStreetMap contributors"). Data is `.js` rather than `.json` so a page still opens straight from disk. Overpass refuses requests with no User-Agent, which the tool sets. A region is just `{name, bbox}`, so adding one is one command plus one entry in the study's region list. The renderer is meant to know nothing about any one region.
